# mission.md — Expense Tracker Frontend

## 1. Мета проєкту

Розробити зручний адаптивний frontend для Expense Tracker API — застосунку для обліку особистих витрат, керування категоріями та перегляду статистики.

Frontend має працювати з уже реалізованим і перевіреним Python/FastAPI backend.

**Основні правила проєкту:**
- Python-код backend не змінювати.
- Не змінювати структуру API та бази даних без окремого погодження.
- MySQL розміщується на зовнішньому хостингу.
- Frontend взаємодіє з базою виключно через backend API.
- Не використовувати демонстраційні дані замість реальних даних API у робочому застосунку.
- Розробку виконувати послідовними ітераціями.
- Після кожної ітерації обов'язково зупинятися та чекати погодження користувача.
- Не починати наступну ітерацію без явного дозволу користувача.
- Рекомендації щодо покращення backend можна надавати, але не реалізовувати без погодження.

## 2. Технології

Основний варіант:
- HTML5.
- CSS3.
- Vanilla JavaScript, без frontend-фреймворків.
- SVG та CSS для графіків і діаграм.
- Fetch API для HTTP-запитів.
- MySQL — зовнішня база даних, доступна через backend.

Не додавати бібліотеки графіків, якщо необхідний результат можна реалізувати простими SVG-елементами та CSS.

Не використовувати складні інструменти або додаткові залежності без обґрунтованої потреби.

## 3. Структура сторінок

### `index.html` — Огляд

Головна сторінка застосунку.

Містить:
- картку загальної суми витрат;
- кількість записів;
- середню витрату;
- мінімальну та максимальну витрати;
- діаграму витрат за категоріями;
- графік витрат за місяцями;
- список останніх витрат;
- кнопку «Додати витрату»;
- переходи до основних розділів.

Статистику отримувати з відповідних endpoint-ів API.

### `expenses.html` — Витрати

Містить:
- таблицю витрат;
- назву, суму, дату та категорію;
- пошук за назвою;
- фільтрацію за категорією;
- сортування за датою або сумою;
- пагінацію;
- створення витрати;
- редагування витрати;
- видалення витрати з підтвердженням.

Форма витрати:
- Назва.
- Сума.
- Дата.
- Категорія.

Перед відправленням перевіряти обов'язкові поля, додатність суми, максимум два знаки після коми та допустимі обмеження backend.

Параметри пошуку, сортування та пагінації узгоджувати з фактичним API.

### `categories.html` — Категорії

Містить:
- список категорій;
- створення категорії;
- перейменування категорії;
- видалення категорії;
- зрозумілі повідомлення про обмеження операцій.

Не дозволяти порожні назви. Обрізати пробіли по краях.

Якщо категорія має пов'язані витрати, показати повідомлення про заборону видалення, коли це підтверджено відповіддю backend.

Не видаляти категорію локально, якщо сервер не підтвердив успішну операцію.

### `statistics.html` — Статистика

Містить три блоки.

**Загальна статистика**
- Кількість витрат.
- Загальна сума.
- Середня витрата.
- Мінімальна витрата.
- Максимальна витрата.

**Статистика за категоріями**
- Назва категорії.
- Кількість витрат.
- Загальна сума.
- Середня сума.

**Статистика за місяцями**
- Місяць у форматі `YYYY-MM`.
- Кількість витрат.
- Загальна сума за місяць.

## 4. Графіки та діаграми

Використовувати SVG і CSS без додаткової бібліотеки на першому етапі.

### Кільцева діаграма категорій

Показувати частку загальної суми витрат для кожної категорії.

Поруч відображати:
- назву категорії;
- суму витрат;
- відсоток від загальної суми.

Використовувати дані endpoint-а статистики за категоріями.

Для нульової суми передбачити порожній стан без помилок обчислення.

### Стовпчикова діаграма місячних витрат

Показувати загальну суму витрат за кожен місяць.

Використовувати дані endpoint-а статистики за місяцями.

Передбачити:
- підписи місяців;
- масштабування стовпчиків;
- підказку із сумою;
- адаптивність;
- коректне відображення порожнього результату.

### Вимоги до графіків

- Не створювати вигаданих даних.
- Не ускладнювати графіки анімаціями.
- Використовувати кольори загальної дизайн-системи.
- Перевіряти відображення на вузьких екранах.
- Забезпечити доступні текстові підписи.
- Якщо SVG виявиться недостатнім для конкретної функції, спочатку запропонувати варіанти й отримати погодження.

Помилки та заборонені дії показувати у власному модальному popup, не використовуючи браузерні `alert()`, `confirm()` чи `prompt()`.

## 7. Поведінка popup-вікон

### Підтвердження видалення

Перед видаленням відкривати власне модальне вікно.

Приклад:

«Видалити цю витрату? Цю дію не можна скасувати».

Кнопки:
- «Скасувати».
- «Видалити».

Якщо операція не дозволена сервером, показати повідомлення з причиною. Не вважати натискання кнопки підтвердження успішним видаленням.

### Помилки

Передбачити зрозумілі повідомлення для:
- `400` — некоректний запит;
- `401` — потрібна авторизація, якщо така вимога існує;
- `403` — дія заборонена;
- `404` — запис або категорію не знайдено;
- `409` — конфлікт або бізнес-обмеження;
- `422` — помилка валідації;
- `500` — внутрішня помилка сервера;
- `503` — сервіс тимчасово недоступний;
- мережевої помилки або недоступності API.

Фактичні статуси й формати помилок перевірити за backend. Не вигадувати неіснуючі відповіді.

Не показувати користувачеві SQL-запити, паролі, stack trace чи інші внутрішні деталі.

## 8. Інтеграція з backend

Backend уже реалізований і перевірений. Його Python-код залишається незмінним.

Очікувані групи endpoint-ів:
- `/categories/`
- `/categories/{id}`
- `/expenses/`
- `/expenses/{id}`
- `/stats/summary`
- `/stats/by-category`
- `/stats/by-month`

Конкретні методи, параметри, типи даних і формати відповідей перевірити за файлами backend перед реалізацією інтеграції.

Створити централізований модуль `api.js`, який відповідає за:
- базову URL-адресу API;
- HTTP-запити;
- JSON-серіалізацію;
- обробку статусів;
- перетворення помилок на зрозумілі повідомлення.

Frontend не повинен напряму підключатися до MySQL.

Підключення до зовнішньої бази залишається відповідальністю backend. Налаштування серверного оточення та секретів не переносити у frontend.

Перевірити доступність API, HTTPS та налаштування CORS відповідно до конфігурації хостингу. Якщо виникає проблема серверної конфігурації, підготувати рекомендацію, не змінюючи Python-код.

## 10. Процес розробки: ітерації та погодження

**Обов'язкове правило:** після завершення кожної ітерації роботу зупинити. Надати користувачеві підсумок, результати перевірок, відомі обмеження та рекомендації. Наступну ітерацію починати тільки після явного погодження.

Результат:

## 11. Формат звіту після кожної ітерації

Після кожної ітерації надавати звіт такого формату:

1. **Що зроблено.**
2. **Які файли створено або змінено.**
3. **Що перевірено і з яким результатом.**
4. **Які проблеми або обмеження залишилися.**
5. **Рекомендації щодо покращення**, окремо позначаючи ті, що стосуються backend.
6. **Що пропонується зробити в наступній ітерації.**
7. **Запит на погодження.**

Після звіту не виконувати жодної роботи з наступної ітерації до відповіді користувача.

Якщо користувач не погоджується, спочатку внести узгоджені зміни в поточну ітерацію та повторно надати результат на перевірку.

## 12. Критерії готовності

Frontend вважається готовим, якщо:
- усі чотири сторінки працюють;
- дані завантажуються з реального API;
- CRUD-операції обробляються коректно;
- статистика та діаграми відповідають даним backend;
- успіх відображається зеленим badge у header;
- помилки й заборонені дії відображаються у власних popup-вікнах;
- видалення вимагає підтвердження;
- інтерфейс адаптований до мобільних і настільних екранів;
- frontend не містить доступів до MySQL;
- Python-код backend не змінений;
- запуск і розгортання документовані;
- усі ітерації пройшли погодження користувача.

## 13. Поза межами початкового обсягу

Без окремого погодження не додавати:
- авторизацію та систему користувачів, якщо їх немає в наявному API;
- зміну схеми бази даних;
- зміни Python-коду;
- додаткові бібліотеки графіків;
- складні анімації;
- нові endpoint-и;
- автоматичне розгортання або платні сервіси.

Будь-яке розширення обсягу спочатку обговорюється з користувачем.
