# Roadmap — Expense Tracker API

## 1. Призначення документа

Цей roadmap побудований на основі `____3_Project_Instructions.pdf`. Він визначає послідовність реалізації проєкту та контрольні результати кожного етапу. Детальні інструкції конкретної ітерації оформлюватимуться окремо у `spec.md` перед початком роботи над нею.

**Правило роботи:** перед кожною ітерацією перевіряти фактичний стан проєкту, не перезаписувати наявну реалізацію без аналізу та не переходити до наступного етапу, доки поточний не перевірений.

## 2. Технології та межі проєкту

- Python і `uv` для керування проєктом та залежностями.
- FastAPI для HTTP API.
- `mysql-connector-python` для роботи з MySQL.
- Pydantic і `pydantic-settings` для моделей та конфігурації.
- MySQL із кодуванням `utf8mb4` та таблицями InnoDB.
- Конфігурація підключення з `.env`.
- Розділення коду на routers, services, repositories, схеми та модулі роботи з базою.

## 3. Послідовність ітерацій

### Ітерація 1 — Ініціалізація проєкту

**Мета:** створити базову Python-структуру та встановити залежності, передбачені інструкцією.

Завдання:
- [ ] Перевірити поточний стан каталогу проєкту.
- [ ] Ініціалізувати проєкт через `uv init`, якщо це ще не зроблено.
- [ ] Додати `fastapi[standard]` і `mysql-connector-python`.
- [ ] Перевірити структуру та конфігурацію залежностей.

**Результат:** проєкт запускається в базовому середовищі, залежності зафіксовані.

**Критерій завершення:** команди середовища виконуються без помилок; наявні файли не дублюються й не перезаписуються без потреби.

### Ітерація 2 — База даних MySQL

**Мета:** підготувати структуру даних відповідно до SQL з інструкції.

Завдання:
- [ ] Створити базу `expense_tracker` з кодуванням `utf8mb4`.
- [ ] Створити таблицю `categories`: `id`, `name`, унікальність назви та перевірка непорожнього значення.
- [ ] Створити таблицю `expenses`: `id`, `title`, `amount`, `spent_on`, `category_id`.
- [ ] Додати перевірки непорожнього заголовка й додатної суми.
- [ ] Додати зовнішній ключ на `categories(id)` з `ON DELETE RESTRICT`.
- [ ] Створити окремого користувача `expense_app` і надати йому права `SELECT`, `INSERT`, `UPDATE`, `DELETE` на `expense_tracker.*`.
- [ ] За потреби завантажити тестові дані: 4 категорії та 6 витрат із PDF.
- [ ] Перевірити структуру таблиць і зовнішній ключ.

**Результат:** база даних і таблиці відповідають схемі з інструкції.

**Критерій завершення:** таблиці створюються, обмеження працюють, зв'язок між витратами й категоріями перевірений.

### Ітерація 3 — Конфігурація та підключення до БД

**Мета:** реалізувати безпечне читання налаштувань і керування з'єднаннями.

Завдання:

- [ ] Реалізувати `app/config.py` на базі `pydantic-settings`, `Settings`, `SecretStr` та кешованої `get_settings()`.
- [ ] Реалізувати `app/database.py`: пул з'єднань розміром 5, `utf8mb4`, заданий SQL mode, timeout 5 секунд і вимкнені multi-statements.
- [ ] Реалізувати залежність `get_conn`: отримання з'єднання з пулу, rollback при винятку та повернення з'єднання через `close()`.
- [ ] Оголосити тип-залежність `Conn`.
- [ ] Перевірити успішне підключення з налаштуваннями з `.env`.

**Результат:** застосунок може отримати з'єднання з MySQL через спільний пул.

**Критерій завершення:** налаштування завантажуються, секрет не виводиться як звичайний текст, з'єднання закривається коректно.

**Результат:** SQL-допоміжні функції та централізовані схеми готові до використання в усіх шарах.

**Критерій завершення:** валідні дані проходять перевірку, зайві поля й недопустимі значення відхиляються.

### Ітерація 5 — Репозиторії

**Мета:** реалізувати SQL-операції для категорій, витрат і статистики.

Завдання:
- [ ] Створити `app/repositories/category_repository.py`: створення, пошук за ID, список, оновлення та видалення категорій.
- [ ] Створити `app/repositories/expense_repository.py`: створення, пошук за ID, фільтрація, сортування, пагінація, оновлення та видалення витрат.
- [ ] Для динамічного `UPDATE` використовувати білий список дозволених полів.
- [ ] Для сортування використовувати лише білий список полів і напрямків.
- [ ] Передавати значення SQL окремими параметрами, а не конкатенувати їх у запит.
- [ ] У пошуку `q` екранувати спеціальні символи `LIKE` (`!`, `%`, `_`) як в інструкції.
- [ ] Створити `app/repositories/stats_repository.py`: загальна статистика, статистика за категоріями та за місяцями.
- [ ] Для статистики категорій зберегти категорії з нульовою кількістю витрат; застосувати `min_count`.
- [ ] Перевірити SQL-операції на тестових даних.

**Результат:** репозиторії ізолюють SQL від бізнес-логіки та HTTP-рівня.

**Критерій завершення:** запити працюють із параметрами, фільтри й сортування відповідають дозволеним значенням, статистичні агрегати коректні.

### Ітерація 7 — HTTP-маршрути та валідація параметрів

**Мета:** надати API-доступ до функцій сервісного рівня.

Завдання:

## 4. Питання з вихідного PDF, які потрібно уточнити перед реалізацією

Ці пункти навмисно не виправляються мовчки в roadmap — у вихідному документі є різні варіанти або приклади, які потрібно узгодити під час відповідної ітерації.

1. **Пароль користувача БД:** інструкція вимагає пароль щонайменше 12 символів, але в SQL і прикладі `.env` наведено `111`, а в `Settings` вказано `min_length=3` із коментарем про `min_length=12`. Перед налаштуванням обрати один узгоджений варіант; для реального використання не залишати прикладовий пароль.
2. **CORS:** у `main.py` наведено варіант із `allow_origins=["*"]` і закоментований варіант із конкретним списком локальних origin. Під час реалізації визначити, який варіант потрібен для поточного середовища.
3. **Тестові дані:** вставки з PDF слід запускати лише тоді, коли це потрібно для перевірки, та враховувати унікальність `categories.name`, щоб повторний запуск не завершувався помилкою дубліката.
4. **Тестування:** PDF описує реалізацію компонентів і приклади SQL/API, але не визначає окремого тестового фреймворку або повного набору автоматизованих тестів. Спосіб автоматизації перевірок слід визначити окремо, не видаючи його за вимогу вихідного документа.

## 6. Дрібні spec-файли та участь користувача

Кожну велику ітерацію розбито на менші специфікації. Деталі наведені в окремому пакеті `expense_tracker_specs`.

| Ітерація | Spec-файли | Участь користувача |
|---|---|---|
| 1. Ініціалізація | `01.1` огляд; `01.2` uv; `01.3` залежності | Підтвердити каталог проєкту; виконати команди локально, якщо вони недоступні асистенту |
| 2. MySQL | `02.1` схема; `02.2` користувач і права; `02.3` тестові дані | **Висока:** виконати SQL у власному MySQL і задати пароль |
| 3. Конфігурація/з'єднання | `03.1` `.env`/Settings; `03.2` пул/Conn | **Висока:** заповнити локальний `.env` і перевірити з'єднання |
| 4. Helpers/схеми | `04.1` SQL helpers; `04.2` Pydantic | Перевірити результати валідації та інтеграції |
| 5. Репозиторії | `05.1` категорії; `05.2` витрати; `05.3` статистика | Перевірити SQL на локальних даних |
| 6. Сервіси | `06.1` категорії; `06.2` витрати; `06.3` статистика | Перевірити бізнес-сценарії після інтеграції |
| 7. Routers | `07.1` категорії; `07.2` витрати; `07.3` статистика | Виконати HTTP-запити через Swagger UI або клієнт |
| 8. Точка входу/помилки | `08.1` lifespan/main; `08.2` errors/CORS | **Потрібне рішення:** обрати CORS для середовища та перевірити запуск |
| 9. Приймання | `09.1` smoke-check; `09.2` крайові випадки | **Висока:** запустити API та надати фактичні результати тестів |

Асистент може підготувати код, SQL і перевірочні запити. Користувач має виконати дії у власному середовищі, які потребують локального MySQL, секретів або підтвердження фактичного запуску. Перевірка користувачем потрібна в усіх ітераціях, але найбільше — у 2, 3 і 9.
